# WIZ Spring 0.2.4

릴리즈 날짜: 2026-07-16

WIZ Spring `0.2.4`는 workspace 설정의 profile 로딩 규칙과 Git 보호 정책을 명확히 하고, Servlet session cookie 설정과 `wiz.yml` workspace metadata를 실제 runtime 동작에 맞게 정리한 패치 릴리즈입니다.

## 주요 변경

- `application.yml`은 공통 설정, `application-<profile>.yml`은 선택된 profile override로 읽는 규칙을 문서화했습니다.
- workspace Java 코드의 `wiz.config().namespace("application")`도 Spring active profile 순서대로 설정을 병합합니다. 여러 profile이 활성화되면 나중 profile의 같은 key가 우선합니다.
- 새 workspace는 실제 `application.yml`, `application-*.yml`을 Git에서 제외하고, 공유용 `application*.example.yml` 세 개를 함께 생성합니다.
- 공통 session cookie 정책을 cookie tracking only, `HttpOnly=true`, `SameSite=Lax`로 명시했습니다.
- 개발 profile은 로컬 HTTP를 위해 `Secure=false`, 운영 profile은 HTTPS 전용 `Secure=true`를 사용합니다.
- logout은 `season.yml`의 별도 key가 아니라 현재 Servlet container의 cookie name/domain/path/HttpOnly/Secure/SameSite/Partitioned 설정을 읽어 같은 cookie를 만료시킵니다.
- 사용되지 않던 `wiz.secret` 생성을 제거했습니다. WIZ Spring 기본 session은 server-side `HttpSession`이며 browser cookie에는 session payload가 아닌 임의의 `JSESSIONID`만 저장됩니다.
- 새 workspace의 `wiz.yml`에 workspace type, metadata format, runtime name과 생성에 사용한 `wiz-spring` 버전을 기록합니다.
- `wiz.yml` metadata를 Java workspace 판별과 MCP workspace status에 사용합니다. 기존 `workspace: java` marker도 계속 호환됩니다.
- CLI, build marker, supply-chain manifest가 JAR manifest의 동일한 runtime version을 사용하도록 버전 판별을 통합했습니다.
- 새 sample에서 사용되지 않던 `database.yml`, `season.yml`과 core 기본값을 그대로 반복하던 generated application 설정을 제거했습니다.

## 0.2.2 이후 기능 변화

`0.2.2`에서 바로 업그레이드한다면 `0.2.3`의 다음 변경도 함께 적용됩니다.

- `create`와 `build`의 `--package-root` 별칭이 제거되었습니다. `--package`를 사용해야 합니다.
- `build --package <package>`는 첫 성공 bundle build 전에만 Java package root를 바꿀 수 있습니다. 이미 개발 중인 workspace의 package를 바꾸는 migration 기능은 아닙니다.
- 새 sample workspace는 표 header만 있는 `devlog.md`와 빈 `devlog/`로 시작합니다. 기존 workspace의 devlog는 수정할 필요가 없습니다.
- Java 21, Maven 3.9, Node.js 22와 개발 도구를 포함한 runtime/bind Docker 개발환경이 추가되었습니다. 기존 로컬 실행 방식에서 Docker로 반드시 전환할 필요는 없습니다.

## 0.2.2 workspace migration

기존 workspace의 `src/`, `pom.xml`, DB 파일을 새로 생성하거나 `wiz-spring create`를 다시 실행하지 않습니다. 새 runtime JAR로 교체하고 아래 config만 기존 custom 값과 병합합니다.

### 1. Runtime 교체

실행 script, alias, service command의 runtime JAR 경로를 바꾸고 버전을 확인합니다.

```bash
runtime=/root/workspace/wiz-java/wiz-spring/target/wiz-spring-0.2.4.jar
workspace=/path/to/existing-workspace

java -jar "$runtime" --version
```

workspace `pom.xml`의 `<version>`은 app artifact 버전이므로 runtime을 사용하기 위해 반드시 `0.2.4`로 바꿀 필요는 없습니다. app release 정책에 따라 별도로 관리합니다.

### 2. application.yml 정리

기존 `server.port`, `wiz.java.package-root`와 실제로 변경한 custom override는 유지합니다. `0.2.2`가 생성한 `wiz.secret`과 core 기본값의 단순 복제는 제거하고 session 공통 정책을 추가합니다.

```yaml
server:
  port: 3000 # 기존 workspace 값을 유지
  servlet:
    session:
      tracking-modes:
        - cookie
      cookie:
        http-only: true
        same-site: lax

wiz:
  java:
    package-root: com.example.app # 기존 package를 유지
```

다음 값은 core 기본값과 같다면 삭제해도 됩니다. 변경해서 사용 중인 값은 유지합니다.

- `wiz.api.prefix`
- `wiz.http.max-request-body-bytes`
- `wiz.socket.*`
- `wiz.redirect.*`
- `wiz.runtime.devmode-cookie-name`
- `wiz.runtime.warmup-enabled`

### 3. profile별 Secure 설정

기존 profile별 custom 값을 보존하면서 다음 block을 병합합니다.

`config/application-dev.yml`:

```yaml
server:
  servlet:
    session:
      cookie:
        secure: false
```

`config/application-prod.yml`:

```yaml
server:
  servlet:
    session:
      cookie:
        secure: true
```

prod session은 HTTPS에서만 정상 동작합니다. HTTP로 prod를 실행하면 browser가 session cookie를 다시 보내지 않습니다. cross-site cookie가 꼭 필요한 경우에만 `SameSite=None`과 `Secure=true`를 함께 사용합니다.

### 4. season.yml과 database.yml 점검

`season.yml`의 다음 generated key는 더 이상 session cookie 설정으로 읽지 않으므로 삭제합니다.

```yaml
session_cookie_name:
session_cookie_path:
session_cookie_http_only:
session_cookie_secure:
session_cookie_same_site:
```

`auth_baseuri`, `pwa_title` 또는 app이 `wiz.config().namespace("season")`으로 직접 읽는 custom key가 있으면 `season.yml` 자체는 유지합니다. `database.yml`도 app이 `wiz.config().namespace("database")`으로 읽는지 먼저 확인하고, 참조가 없을 때만 삭제합니다.

### 5. wiz.yml metadata 갱신

기존 `workspace: java` 한 줄 marker도 계속 동작하지만, 판별 정보와 MCP status를 위해 다음 형식으로 갱신하는 것을 권장합니다.

```yaml
workspace: "java"
format-version: 1
runtime:
  name: "wiz-spring"
  version: "0.2.4"
```

기존 workspace에서는 이 값을 수동으로 갱신합니다. `runtime.version`은 마지막으로 migration한 runtime의 기록이며 runtime 실행 때 자동으로 덮어쓰지 않습니다.

### 6. Git 보호와 example 파일

`.gitignore`에 다음 규칙을 추가합니다.

```gitignore
/config/application.yml
/config/application.yaml
/config/application-*.yml
/config/application-*.yaml
!/config/application.example.yml
!/config/application.example.yaml
!/config/application-*.example.yml
!/config/application-*.example.yaml
```

실제 설정을 기준으로 credential, token, 내부 endpoint를 제거한 `application.example.yml`, `application-dev.example.yml`, `application-prod.example.yml`을 만듭니다. 실제 설정이 이미 Git에 올라가 있다면 ignore 규칙만으로는 추적이 중단되지 않습니다.

```bash
git rm --cached --ignore-unmatch config/application.yml config/application-*.yml
git add .gitignore config/application*.example.yml config/wiz.yml
```

example 파일을 `git add`하기 전에 실제 비밀 값이 제거됐는지 반드시 확인합니다. 기존 repository history에 실제 credential이 있었다면 파일 untrack과 별개로 credential rotation도 수행합니다.

### 7. clean build와 동작 확인

profile config가 bundle에 다시 들어가도록 clean build합니다.

```bash
java -jar "$runtime" build --root "$workspace" --clean
java -jar "$runtime" run --root "$workspace" --profile dev
```

standalone artifact를 배포한다면 새 runtime으로 다시 패키징합니다.

```bash
java -jar "$runtime" jar --root "$workspace" --clean --output /tmp/wiz-app.jar
```

확인 항목:

- dev 응답 cookie: `HttpOnly`, `SameSite=Lax`, `Secure` 없음
- prod HTTPS 응답 cookie: `Secure`, `HttpOnly`, `SameSite=Lax`
- `/auth/logout`이 실제 cookie name/path/domain으로 만료 cookie를 반환하는지
- app에서 `wiz.config().namespace("application")`을 사용한다면 profile override로 값이 바뀌는 부분이 없는지
- standalone JAR과 bundle에 불필요한 credential이 포함되지 않았는지

## 호환성 주의사항

- 새 `.gitignore` 정책은 기존 tracked config를 자동으로 untrack하지 않습니다.
- `application-<profile>.yml`의 값이 이제 workspace Java config API에도 반영되므로 base/profile에 같은 key가 있는 app은 동작을 다시 확인합니다.
- 기본 session 저장소는 process memory입니다. 재시작 후 session 유지나 여러 instance의 session 공유가 필요하면 Spring Session Redis/JDBC 같은 공용 저장소를 별도로 구성합니다.
- `build --package`는 이미 첫 bundle build가 끝난 `0.2.2` workspace의 package 변경에 사용할 수 없습니다.
